# 原型结论（2026-11-22，全部虚构语料，DeepSeek 线上主模型）

问题：付款节点改成「LLM 给结构 + 代码核与版式无关的不变量」，能否少写正则、又不放过错拆？

结论：在这批虚构语料上能。
- **错拆**：LLM 三轮独立调用都是 0；正则有 2 条（`虚构首批即停案J` 50→100 被拆成一个 0→100；`留出_质保金写在前面` 拆成 5→55→100）。
- **覆盖**：没为之写过规则的 23 条变体里，LLM 认对 18 条、正确放弃 5 条；正则认对 5 条、放弃 12 条、错拆 1 条。
- **不变量拦截**：把 LLM 的正确输出故意改错，约 860 次篡改 0 漏过（比例看错、片段改字、本期 / 累计弄反、漏节点、排除项丢失；编号由代码定，改模型的编号不影响结果）。
- **分工**：编号不交给 LLM，由代码按片段在原文中的位置、用现有编号规则确定（编号决定「第3.1.4条」这类引用格式，属于有限的决策层）。最初让 LLM 给编号，虚构安装案H 的「4.2 ……第一期……」被引成「第一期」，端到端比对才发现。
- **端到端**：两种拆法各走一遍现有派生规则，与律师诉状比对（payable_ratio / payment_cite_location / payment_cite_text），在虚构案卷集上 LLM 与正则全部一致，另多认出 3 个案件的条款（`real_cases.py`）。
- **代价**：每案多一次文字 LLM 调用。

注意：
- 不变量是看着这批语料调了五轮的；heldout2 写于第二轮之后，严格说也不算完全干净的留出集。heldout / heldout2 的标注是原型作者按字面手标的，未经律师确认。
- 下游引用只在虚构案卷集的 9 个有标准引用的案件上比过；一体化合同选段沿用现有代码，没有改。
- 还没在服务器上的真实案卷（真实 OCR 文本）上跑过，这是能否落地的关键一步：`real_cases.py`。

复现：`python scripts/proto_payment_nodes_llm/run.py --cache <目录>`（需 DEEPSEEK_API_KEY）；`mutate.py --cache <目录>` 跑篡改测试。
